# PR, CI, wydanie i przekazanie

Szczegóły obowiązujących zasad z [AGENTS.md](../../AGENTS.md); dokument jest jego częścią, nie osobnym źródłem zgód. Numeracja § odsyła do AGENTS.md. Czytaj tylko przy pracy objętej poniższym zakresem. Przeniesione procedury zachowują daty decyzji.

## 12. PR, CI i scalanie — zatwierdzona procedura (2026-10-15)

Ta sekcja jest obowiązująca również **na początku nowych wątków**. W razie rozbieżności ze starszymi raportami lub planami o Draft PR decyduje aktualna procedura i rzeczywisty plik `.github/workflows/preflight-js.yml`.

- **Nie twórz Draft PR jako domyślnego etapu.** Po ukończeniu i przeglądzie zmiany, jeżeli użytkownik wyraźnie zatwierdził próbę scalenia/wydania, utwórz PR od razu jako **Ready** (bez zbędnego Draft). Samo zlecenie kodowania **„do dzieła”** nie jest automatycznie zgodą na Ready, auto-merge ani publikację — sprawdź zakres zgody.
- Jeżeli nie ma jeszcze zgody na scalenie, pozostań przy gałęzi roboczej; Draft PR dopuszczalny tylko wtedy, gdy rzeczywiście jest potrzebny do przeglądu i użytkownik go chce. Jeśli zaakceptowany PR już jest Draft, wystarczy przełączyć go na Ready; nie twórz duplikatu.
- **„Wydaj” = zgoda właściciela (22.11.2026).** Samo to polecenie zatwierdza jedną próbę wydania przygotowanego, jednoznacznie wskazanego pakietu. Nie wymagaj pełnego zdania, przepisywania SHA ani ponownej zgody na tę samą próbę. Przed operacją wykonawca weryfikuje i zapisuje repo/gałąź/dokładne HEAD/BASE/zakres. Niejasny wybór pakietu lub zmiana SHA wymaga rozstrzygnięcia; poprzednie „wydaj” nie zatwierdza automatycznie kolejnych rewizji ani retry. Pozostałe bramki i odrębność Firebase LIVE pozostają w mocy.
- **Stały wyjątek operacyjny — PR Ready obsługuje ChatGPT (2026-10-21).** Po **każdorazowej, osobnej zgodzie właściciela** na konkretną próbę wydania (repozytorium, gałąź, dokładne HEAD i BASE SHA oraz zakres), ChatGPT może samodzielnie utworzyć **jeden PR bezpośrednio jako Ready** przez połączony GitHub, aby ograniczyć zużycie limitu Codexa. Przed operacją odczytowo weryfikuje wskazane SHA, diff, wymagane pokrycie CI oraz istnienie i stan PR (nowy tworzy wyłącznie przy braku istniejącego); zmiana któregokolwiek warunku oznacza STOP i potrzebę nowej zgody. Po utworzeniu PR ChatGPT wyłącznie odczytowo obserwuje wyniki CI, automatyczny merge i Pages. **Nie** zmienia w tym trybie plików, commitów, gałęzi, workflow ani testów, **nie** scala ręcznie, nie ponawia prób i nie wykonuje żadnych operacji Firebase LIVE. Samo to upoważnienie **nie jest** zgodą na żadne konkretne wydanie. Jeżeli bezpośrednia obsługa PR przez ChatGPT jest niedostępna, Codex albo właściciel może wykonać tę samą operację wyłącznie po uzgodnieniu wykonawcy, nadal z osobną zgodą na wydanie.
- **Naprawa FAIL istniejącego PR — decyzja właściciela 19.11.2026.** Po osobnej zgodzie na zakres naprawy Codex domyślnie implementuje i testuje bezpośrednio na gałęzi tego samego PR. Nie tworzy dodatkowej gałęzi naprawczej ani etapu późniejszego fast-forward: kończy jednym spójnym commitem i zwykłym pushem. Najpierw zapisuje zweryfikowane wejściowe HEAD gałęzi PR i BASE/main; ponawia odczyt GitHuba bezpośrednio przed pushem. Zmiana któregokolwiek z nich przez innego wykonawcę oznacza STOP, zachowanie lokalnej pracy i raport — bez force-push, nadpisywania, automatycznego rebase/merge. Sam własny commit tworzy raportowany nowy HEAD, a nie zgodę wydaniową. Raport każdej naprawy zawiera aktualne zdalne HEAD/BASE, wykonane testy i ich ograniczenia, CLEAN/push oraz stan PR (otwarty/zamknięty, Draft/Ready, scalony/niescalony). Nie zmienia się Draft/Ready, nie uruchamia Actions ani retry. Ten osobno zatwierdzony tryb implementacyjny nie zmienia odczytowej roli ChatGPT podczas wcześniejszej próby wydania. Po naprawie nadal potrzebne są kontrola techniczna Codexa i osobna zgoda właściciela na każde wydanie dla dokładnych nowych SHA; obowiązują jedno pełne CI, auto-merge wyłącznie po PASS i kontrola Pages.
- **Jedno uruchomienie CI w GitHub Actions na zatwierdzoną próbę:** zdarzenie `opened` dla niedraftowego PR lub `ready_for_review` przy przejściu Draft → Ready. Domyślnie pełny Preflight. Zatwierdzona optymalizacja 22.11.2026: safety klasyfikuje dokładny diff HEAD/BASE; wyłącznie modyfikacje zwykłych plików 100644 `AGENTS.md`, `CURRENT_STATE.md`, `docs/agents/RELEASE.md` kwalifikują się do ścieżki `documents`. Każdy inny plik (także workflow/test/klasyfikator), rename, dodanie, usunięcie lub zmiana trybu wymusza `full`. Documents ponownie sprawdza zamknięty zakres, treść/odnośniki w zatwierdzonym drzewie, niezmienność aplikacji, 425 pinów i odmowy aktualnych źródeł. Agregaty wymagają sukcesu oraz potwierdzonego wyniku documents; nie wykonują i nie przypisują PASS testom SDK/aplikacji. Nieznany zakres/brak dowodu = RELEASE_BLOCKED. Pozostałe bramki SHA/Ready/auto-merge/exact Pages są wspólne. Utworzenie Draft, push (`synchronize`) i merge nie ponawiają Preflightu. Bez zatwierdzonej próby pakiet pozostaje `CODE_READY` / `CI_PENDING`; Codex nie dubluje pełnego CI lokalnie.
- Przed Ready sprawdź faktyczne pokrycie wymaganych testów dla zatwierdzonego HEAD/BASE oraz wykonanie przeglądu i dostosowania istniejących testów powiązanych ze zmianą, zgodnie z AGENTS.md §3 (w tym statycznych kontroli, fixture i zależności). Jeżeli brakuje zadania wysokiego ryzyka, przygotuj właściwą kontrolę CI w uzgodnionym zakresie przed próbą wydania; nie zastępuj jej deklaracją ani PASS innej gałęzi. Ręczny `workflow_dispatch` nie stanowi obejścia zgody ani powodu do ponownego pełnego CI.
- Workflow po wszystkich obowiązkowych kontrolach właściwych dla zweryfikowanego zakresu (`full` albo ściśle dokumentacyjny `documents`) **automatycznie scala** PR, wyłącznie jeśli `head SHA` i `base SHA` są identyczne ze stanem zatwierdzonej próby. Błąd, brak dowodu zakresu, zmiana gałęzi lub cofnięcie do Draft blokują merge. Nie wykonuj drugiego, ręcznego merge „dla pewności” i nie omijaj zabezpieczeń.
- Po merge workflow sprawdza GitHub Pages **dla dokładnego merge SHA** bez kolejnego pełnego Preflightu. Rozróżniaj: PR scalony, CI PASS i Pages PASS; nie deklaruj wdrożenia jako gotowego, jeśli Pages nie zostało potwierdzone.
- Każda zmiana `head SHA`, ponowienie po FAIL oraz nowa próba wdrożenia wymagają nowej świadomej zgody użytkownika. Nie uruchamiaj ukrytego auto-merge z samego commita lub automatycznego ponowienia.
- Każdy nowy wątek dotyczący Meble-App powinien przed proponowaniem Ready/merge sprawdzić aktualne `AGENTS.md`, `CURRENT_STATE.md`, dokumenty decyzji i faktyczny workflow. Starsze zasady „obowiązkowy Draft PR” nie są już aktualne. Pozostałe zasady ochrony danych, UI oraz planowania zmian pozostają w mocy.

## 16. Wydania: aktualizacja klienta, monolity, równoległe CI — decyzja 31.10.2026

**Wersja widoczna u użytkownika jest obowiązkową częścią wydania, niezależną od PASS GitHub Pages.** Przy zmianie aplikacji aktualizuj spójnie wersje zasobów `?v=`, manifest offline i powiązane sumy integralności; nie wystarczy sam merge. Mechanizm aktualizacji ma wykrywać dostępne wydanie, pokazywać użytkownikowi komunikat **„Dostępna nowa wersja — odśwież”** i bezpiecznie przeprowadzać stary Service Worker do nowej wersji bez utraty danych. Nie wolno wymuszać przeładowania podczas niezapisanego formularza, aktywnej edycji lub niepotwierdzonego zapisu offline. Usuwanie starych zasobów dopiero po dowodzie, że nie kontrolują już aktywnej sesji. Żadnego czyszczenia IndexedDB, localStorage inwestorów/projektów/cenników, resetów urządzenia ani ukrytych migracji. Wymagana regresja real Chromium: **stary worker i dane tego samego profilu → nowy deploy → wykrycie wersji → bezpieczna aktualizacja → widoczna nowa funkcja + zachowane dane**. Ten kontrakt jest obowiązujący; jego pełna automatyzacja w produkcie wymaga oddzielnej implementacji i testu, nie wolno udawać, że sam cache-busting już go spełnia.

**Kontrola rozrostu kodu i odpowiedzialności:** bazą są istniejące progi z `tools/dependency-audit-lib/scan-dependencies.js`: **250+ linii = ostrożność, 400+ = ostrzeżenie/analiza, 600+ = wysoki koszt ryzyka i konieczność uzasadnienia przed rozbudową**. Nie mieszać w jednym nowym module renderowania/UI, bezpośredniego storage, domeny, recovery i orkiestracji. Przekroczenie progu 600 linii przez nowy moduł produkcyjny lub rozrost starego modułu 600+ z mieszaną odpowiedzialnością jest blokowane przez kontrolę przyrostu, zamiast blokowania istniejącego kodu tylko za jego rozmiar. Wyjątki wymagają uprzedniej, osobnej decyzji właściciela oraz kontraktu regresji; sam wzrost liczby linii nie usprawiedliwia automatycznego refaktoru. Kontrola obejmuje też raportowanie rozrostu kodu testowego. Nie dokładać funkcji do monolitu wyłącznie dlatego, że łatwiej ją tam umieścić.

**Budżet wydajności GitHub CI:** akceptacyjna granica **poniżej 120 s wykonywania każdej grupy/niepodzielnego scenariusza**, docelowo **75–90 s** z zapasem; po **75 s** i **90 s** pokazywać czytelne ostrzeżenie z prośbą o ocenę/optymalizację. **Przekroczenie czasu wymaga dalszej optymalizacji i ponownego pomiaru, ale nigdy samo nie daje FAIL, nie przerywa testu ani nie unieważnia PASS.** Realne FAIL to błąd testu, integralności, niepełne pokrycie, niepotwierdzona grupa albo brak wymaganych zabezpieczeń. Czas uruchomienia runnera, instalacji zależności, scalenia i Pages mierzyć i raportować osobno od czasu samych testów; nie obiecywać 90 s całego wydania.

**Wszystkie długie testy uruchamiać równolegle tam, gdzie są niezależne:** Preflight ma 36 deterministycznych grup smoke, obejmujących wszystkie pliki, także kompletne części dawnych testów >120 s; kontroluje pełny przydział każdego wariantu, z izolacją przeglądarek. Firebase Current obejmuje osiem niezależnych, obowiązkowych segmentów emulatora DEMO (dwa dla pierwotnej grupy 1, jeden dla grupy 2 i pięć dla grupy 3); historyczny smoke i SDK to osobne zadania. Każdy test i plik SDK musi należeć do dokładnie jednej obowiązkowej grupy, również po dodaniu nowych testów. Brak grupy, pominięcie/skipped, failed, niekompletne TAP, zmieniony HEAD/BASE, 425 pinów, naruszenie immutability historycznej lub błąd ochrony danych = **RELEASE_BLOCKED**. `ci-summary` i auto-merge uwzględniają pełne zestawy, nigdy tylko najszybszy shard. Bez automatycznych retry, bez omijania testów; kalkulować również koszt większej liczby runnerów. Zmiany workflow nie uruchamiają ani ponawiają CI bez osobnej zgody właściciela na konkretne HEAD/BASE.

**Czas każdego wydania — decyzja właściciela 22.11.2026 (uzupełnia kalibrację 21.11):** po każdej próbie analizuj i krótko raportuj rzeczywisty czas ścienny od zgody właściciela/rozpoczęcia obsługi wydania do potwierdzonego exact Pages i kontroli opublikowanych plików. Osobno podaj przygotowanie/PR, safety, kolejkę i instalację runnerów, testy, podsumowania, merge oraz Pages/weryfikację; etapy równoległe mogą się nakładać, suma runner-sekund nie jest czasem całego wydania. Podawaj punkty początku/końca i źródła znaczników; jeśli brak czasu zgody, użyj najwcześniejszego dostępnego zdarzenia (np. PR/Ready), jawnie oznacz niezmierzony odcinek i nie przedstawiaj tego jako pełnego pomiaru. Przy FAIL mierz do zakończenia próby, bez sugerowania publikacji.

Cel to maksymalnie **4 minuty całego wydania**. Powyżej 240 s obowiązkowo wskaż dominujące opóźnienia i zaproponuj konkretne optymalizacje z dowodami, szacowanym zyskiem oraz ograniczeniami; nie wdrażaj zmian bez zgody właściciela. Zachowaj 36 logicznych grup i wszystkie przypadki; plan kalibruj rzeczywistymi pomiarami, jawnie oznaczając szacunki. Cache dopuszczalny wyłącznie dla publicznych pobrań przypiętych zależności: npm ci z integralnością oraz JAR sprawdzony według metadanych przypiętego CLI. Bez cache danych aplikacji/profili/poświadczeń, skracania asercji czasu rzeczywistego, retry ani pomijania bramek. Cache miss nie jest FAIL, uszkodzony cache odmawia. Kolejki GitHuba i zimny cache mogą przekroczyć cel; nie gwarantuj 4 minut bez pomiaru kompletnego wydania. [Pomiar #1367 i ograniczenia](../../tools/reports/preflight-1367-repair-speed-20261121.md).

**Rozdział wykonania i zgód:** te zasady są trwałe we wszystkich kolejnych wątkach; ChatGPT kontroluje ich przestrzeganie niezależnie od pamięci konwersacji. Standardowo programuje Codex, ale po **odrębnej, wyraźnej zgodzie na określony zakres** ChatGPT może wyjątkowo implementować kod i zapisać osobną gałąź/commit; nie daje to domyślnej zgody na PR Ready, CI, merge, Pages, migrację lub Firebase LIVE.

## 20. Stały protokół przekazania do wydania — decyzja właściciela 03.11.2026

Po zakończeniu każdego zatwierdzonego zadania Codex:

1. Kończy implementację, wykonuje wymagane testy celowane i aktualizuje `CURRENT_STATE.md` oraz właściwy istniejący raport. Nie dubluje pełnego CI (AGENTS.md §3).
2. Wykonuje commit i push na gałąź roboczą oraz potwierdza czyste drzewo. Przy zatwierdzonej naprawie FAIL istniejącego PR jest to domyślnie bezpośrednio gałąź tego PR, z ponowną kontrolą wejściowych HEAD/BASE i STOP przy obcej zmianie (§12).
3. Bezpośrednio przed przekazaniem sprawdza aktualny GitHub: dokładny HEAD gałęzi roboczej oraz BASE docelowego `main`. Podaje pełne SHA 40 znaków potwierdzone zdalnie; nie używa nieaktualnych SHA z pamięci lub dokumentacji.
4. Przekazuje krótki raport gotowy do skopiowania do ChatGPT, według wzoru poniżej, z aktualnym HEAD/BASE, faktycznymi testami i stanem PR. Wyniki dotyczą faktycznie wykonanych kontroli; wcześniejszy PASS oznacza wraz z jego SHA i nie przypisuje go automatycznie do nowego HEAD (AGENTS.md §10). Dla zmian wyłącznie dokumentacyjnych wystarcza właściwa kontrola diffu; nie ponawia testów aplikacji bez nowej przyczyny.
5. Nie tworzy PR, nie uruchamia GitHub Actions, nie scala ani nie publikuje samodzielnie i nie wykonuje Firebase LIVE. Wydanie obsługuje ChatGPT: wyłącznie obsługuje wydanie przygotowanego przez Codexa pakietu, po osobnej zgodzie właściciela na dokładny HEAD/BASE obsługuje jeden PR Ready (istniejący PR zachowuje, bez tworzenia duplikatu) i odczytowo obserwuje CI, auto-merge oraz GitHub Pages (AGENTS.md §12). Awaryjne zastępstwo wykonawcy wymaga osobnego uzgodnienia; nie jest domyślną częścią implementacji.

Jeżeli zadanie jest niedokończone albo wymagane testy nie przeszły, raportuj **BLOCKED**, wskaż konkretną przyczynę i nie przedstawiaj pakietu jako gotowego do wydania. `CODE_READY / CI_PENDING / RELEASE_BLOCKED` oznacza gotowość do kontroli pakietu; nie jest zgodą ani dowodem wydania. Każda późniejsza zmiana HEAD/BASE wymaga nowego przekazania i osobnej zgody wydaniowej.

Obowiązkowy format przekazania (pola w nawiasach zastąpić faktami):

```text
MEBLE-APP — PAKIET DO WYDANIA

Repo: mebleszek/meble-app
Gałąź: [nazwa]
HEAD: [pełny SHA 40 znaków]
BASE/main: [pełny SHA 40 znaków]
PR: [numer albo brak; otwarty/zamknięty, Draft/Ready, scalony/niescalony]

Status: CODE_READY / CI_PENDING / RELEASE_BLOCKED

Zmiany:
[2–4 zdania, co faktycznie zrobiono]

Testy:
[nazwy i rzeczywiste wyniki PASS/FAIL; BLOCKED, jeśli wymaganej kontroli celowanej nie wykonano]

Ograniczenia:
[co nadal nie działa, co jest zablokowane]

Drzewo robocze: CLEAN
Commit i push: POTWIERDZONE

Przekazanie: Pakiet gotowy do kontroli wydania przez ChatGPT. Wymagana osobna zgoda właściciela na dokładny HEAD/BASE.
```

Dla pakietu zablokowanego zastąp status i zdanie „Przekazanie” jednoznacznym **BLOCKED** z przyczyną; nie deklaruj CLEAN/push, jeżeli nie zostały faktycznie potwierdzone.
